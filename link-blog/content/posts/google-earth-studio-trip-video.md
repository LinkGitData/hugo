## 🏗️ 整體製作管線與五階段架構設計

### 為什麼不在 Google Earth Studio 裡直接畫路線？

許多人初次接觸 Google Earth Studio 時，會直覺想把 KML 軌跡檔直接匯入成疊加層（Overlay）。然而在實測中會發現兩個致命限制：
1. **不支援動態繪製（Animated Reveal）** ：Earth Studio 的 KML 疊加層官方主要針對地標、點與多邊形設計，對於 `LineString` 路線只能整體調整透明度， **無法做到「路線跟著鏡頭逐步畫出」** 的動態效果。
2. **地圖原生標籤與自訂資訊衝突** ：若開啟預設地圖資訊，密密麻麻的道路編號與小地名會與我們的路線、景點膠囊標籤重疊，導致畫面雜亂不堪。

因此，我們採用 **「算繪與後製分離」** 的架構設計：讓 Earth Studio 專心負責「拍出乾淨的 3D 衛星實景畫面」並匯出每一格的 **3D 追蹤鏡頭資料（Camera Tracking JSON）** ，再透過 Python 腳本將經緯度軌跡透過 3D 透視投影（Perspective Projection）精準疊加到每一格畫面上。

### 五大步驟職責與解耦優勢

| 階段 | 解決的核心問題 | 輸入資料 | 輸出產物 | 若跳過此步驟的後果 |
| :--- | :--- | :--- | :--- | :--- |
| **步驟一：準備軌跡** | 將 KML 中零散的移動段與停留點，整理為每天一條依時間排序、排除跨洲飛行並算妥累積距離的連續路徑 | `test123_actual_track.kml` | 記憶體中的每日路徑、Haversine 累積距離、交通模式 | 路徑順序錯亂、返台班機把鏡頭拉到亞洲、無法依距離分配時間 |
| **步驟二：產生專案檔** | 扮演「虛擬導演」，決定每個時間點鏡頭位置、高度與目標點（POI），產生 `.esp` 與共用時間表 | 每日路徑、17 個景點座標清單 | `.esp` 專案檔、 `.timing.json` 時間表 | 需在 Earth Studio 手動設定 639 組關鍵影格 × 6 個屬性，人工無法達成 |
| **步驟三：Earth Studio 算繪** | 運用 Google Earth 3D 衛星與建築模型算繪實景畫面，並匯出每一格的 **實際** 鏡頭座標 | `.esp` 專案檔 | `4,786` 張 JPEG 序列、鏡頭追蹤 JSON | 缺乏 3D 實景底圖；若無匯出鏡頭 JSON，自行內插的誤差最高達 57% |
| **步驟四：畫路線並合成** | 逐格投影繪製抗鋸齒彩色路線、交通 Emoji 圖示、景點膠囊標籤、日期字幕與結尾出處面板 | JPEG 序列、鏡頭 JSON、 `.timing.json` 、KML | 無聲 MP4 影片 | 只有空拍風景，觀眾看不出走了哪條路、現在是第幾天、地標是什麼 |
| **步驟五：加上配樂** | 結合合法授權的古典樂錄音，執行 EBU R128 響度標準化，讓影片結尾與最後一個和弦完美同步 | 無聲影片、 `music/summer_presto.oga` | `trip_full_route_v4_music.mp4` | 影片缺乏情緒張力，或因直接裁切音樂導致樂曲突兀中斷 |

> 💡 **經驗分享** ：
> **「步驟三只負責拍，步驟四才負責畫」** 是整套工作流最關鍵的工程決策。在 Earth Studio 算繪 4,786 格需要 30 分鐘以上，但步驟四用 Python 多核心合成只需約 5 分鐘。當我們需要調整字幕字型、路線線寬、標籤位置或結尾出處排版時， **完全不必重新算繪 3D 畫面** ，只要重跑步驟四即可快速迭代！

## 💻 核心演算法揭秘：從 .esp 自動運鏡到 3D 透視投影

### 1. 非線性時間分配與 Smoothstep 緩動（ `make_esp.py` ）

若將移動時間與距離設為線性正比，`330 km` 的跨國開車日會佔去整支影片一半以上的時間，而 `15 km` 的布拉格老城漫步則會在 0.5 秒內一閃而過；反之若每天平均分配，高速公路移動又會快到令觀眾眼花。因此我們設計了雙層次非線性時間分配模型：

1. **每日時間預算 ∝ `√(當日總距離)`** ：以 **距離的平方根** 分配 100 秒的純移動預算，兼顧長途自駕與城市漫步的觀看體驗。
2. **日內分段（Leg）時間 ∝ `分段距離^0.7`** ：在每天內部依景點切分為多個移動段，每段最短保底 `0.8 秒` ，並在每天開頭停頓 `1.0 秒` 、每個景點停留 `2.5 秒` 。
3. **Smoothstep 緩動內插** ：將每天的進度表示為一串節點（Knots） `(時間 t, 累積距離 s)` ，節點之間使用三次多項式 `s(u) = u² × (3 − 2u)` 進行緩動，使鏡頭在進入景點前自然減速、離開景點時平滑加速：

```python
def ease(u):
    u = min(1, max(0, u))
    return u * u * (3 - 2 * u)

def interp_knots(knots, t):
    """計算時間 t 的累積行進距離 s(t) 與瞬時速度 ds/dt"""
    if t <= knots[0][0]:
        return knots[0][1], 0.0
    for (ta, sa), (tb, sb) in zip(knots, knots[1:]):
        if t <= tb:
            if tb == ta:
                return sb, 0.0
            u = (t - ta) / (tb - ta)
            # 導數 ds/dt = (sb - sa) / (tb - ta) * 6u(1 - u)，供動態鏡頭高度計算使用
            return sa + (sb - sa) * ease(u), (sb - sa) / (tb - ta) * 6 * u * (1 - u)
    return knots[-1][1], 0.0
```

### 2. 速度耦合鏡頭高度與 970 km 垂直總覽計算

畫面上的地面視覺捲動速度約等於 **「實際移動速度 ÷ 鏡頭高度」** 。為了不讓觀眾一下暈車、一下覺得畫面停滯，我們的演算法讓鏡頭高度隨當下移動速度動態伸縮：

* **動態巡航高度** ：`高度 ≈ 當下移動速度 × 1.3` （公尺／動畫秒），限制在 `1,500 m` 至 `45,000 m` 之間，並在對數空間（Log-space）執行 `±0.75 秒` 的滑動視窗平滑化，讓俯衝與拉升極度自然。
* **景點放大高度** ：抵達景點前後 1 秒內，高度降至 `max(1500, 2.5 × 軌跡至景點距離, 個別指定高度)` ，確保即使軌跡離景點有一段距離（如佩特任瞭望塔相距 `626 m` ），路線前端與景點依然能同時收進畫面。
* **970 km 總覽高度幾何推導** ：整趟旅程南北跨度約 `285 km` 、東西跨度約 `260 km` 。要將整條路線放進 `16:9` 畫面並保留 `20%` 邊界，已知 Earth Studio 垂直視角 `fovVertical = 20°` ，總覽高度計算公式為：
  `總覽高度 = 跨度範圍 × 1.2 ÷ (2 × tan(視角 / 2)) ≈ 970 km`
  同時在開場與結尾總覽時將鏡頭傾角（Tilt）漸變為 `0°` （正下方垂直俯視），使結尾畫面如同一張清晰的巨幅地圖。

### 3. 逆向工程 `.esp` 專案格式與 POI 鏡頭目標控制

Google Earth Studio 的 `.esp` 專案檔為 `modelVersion: 18` 的 JSON 結構。我們不直接計算容易產生萬向鎖與側滾（Roll）誤差的歐拉角（Heading / Tilt），而是同時寫入 **「攝影機座標（Camera Position）」** 與 **「鏡頭目標點（Point of Interest, POI，設定 `influence: 1` ）」** 兩組關鍵影格，交由 Earth Studio 自動解算視線方向，並將所有數值與時間正規化至 `[0, 1]` 區間：


### 4. WGS84 ECEF 座標轉換與 3D 相機透視投影（ `route.py` ）

在步驟四合成時，我們讀取 Earth Studio 匯出的 `trip_earth_studio_v4.json` 中每一格的真實經緯度與高度（ `coordinate` ），結合 `.esp` 內的 POI 關鍵影格，在 **WGS84 地心地固座標系（ECEF）** 中重建每一格的相機正交基底 `(right, camUp, forward)` ，將所有 GPS 軌跡點投影至 `1920×1080` 像素平面：

```python
def ecef(lat, lon, h):
    """將 WGS84 經緯度與海拔高度轉換為 ECEF 三維直角座標 (X, Y, Z)"""
    a, e2 = 6378137.0, 6.69437999014e-3
    la, lo = np.radians(lat), np.radians(lon)
    n = a / np.sqrt(1 - e2 * np.sin(la) ** 2)
    return np.stack([
        (n + h) * np.cos(la) * np.cos(lo),
        (n + h) * np.cos(la) * np.sin(lo),
        (n * (1 - e2) + h) * np.sin(la)
    ], axis=-1)

def camera(self, frame, W, H):
    """還原第 frame 格的相機位置 C 與正交座標系 (fwd, right, cup)"""
    c = self.cam[frame]['coordinate']
    C = ecef(c['latitude'], c['longitude'], c['altitude'])
    P = ecef(*(catmull(k, frame) for k in self.poi))
    la, lo = math.radians(c['latitude']), math.radians(c['longitude'])
    # 地表法向量 up，確保相機無側滾（No Roll）
    up = np.array([math.cos(la) * np.cos(lo), math.cos(la) * math.sin(lo), math.sin(la)])
    fwd = P - C; fwd /= np.linalg.norm(fwd)
    right = np.cross(fwd, up); right /= np.linalg.norm(right)
    cup = np.cross(right, fwd)
    focal = (H / 2) / math.tan(math.radians(self.cam[frame]['fovVertical']) / 2)
    return C, fwd, right, cup, focal
```

接著由 `compose.py` 使用 **2 倍超取樣（2x Supersampling）** 繪製深色外框與彩色抗鋸齒路線，疊上 `Apple Color Emoji.ttc` 交通圖示與 `PingFang.ttc` 繁體中文字卡，最後交由 `ffmpeg` 編碼輸出。

## ☁️ 延伸架構：以 Cloud Run 與 3D Tiles 打造全自動化雲端服務

完成單機版自動化管線後，如果我們想將這套工具封裝成讓使用者「上傳 `Timeline.json` 即可自動生成 3D 旅遊影片」的雲端服務，最大的架構限制在於： **Google Earth Studio 並沒有提供官方 API** ，只能在瀏覽器中登入操作。為此我們規劃了兩階段的雲端演進藍圖：

{{< mermaid >}}
flowchart TD
    User[使用者上傳 Timeline JSON] --> API[Cloud Run 前端與 API 服務]
    API --> Parse[解析軌跡與 Places API 查詢景點真實座標]
    Parse --> State[Firestore 記錄任務狀態]
    Parse --> WF[Cloud Workflows 編排調度]

    subgraph PlanB[全自動算繪與平行合成管線]
        WF --> GPUJob[Cloud Run Job 搭載 NVIDIA L4 GPU]
        GPUJob --> Cesium[無頭 Chrome 與 CesiumJS 載入 Photorealistic 3D Tiles]
        Cesium --> WaitTile[逐格定位鏡頭並等待 tilesLoaded 完成後截圖]
        WaitTile --> CPUJob[Cloud Run Job 多 Task 平行 CPU 合成]
        CPUJob --> Encode[疊加字幕圖示與 FFmpeg 分段編碼合併]
    end

    Encode --> GCS[Cloud Storage 儲存成品並設定 7 天自動刪除]
    GCS --> SignedURL[產生簽章下載連結並透過 PubSub 通知使用者]
{{< /mermaid >}}

1. **方案 A（半自動混合雲架構）** ：
   將現有的 `make_esp.py` 部署為 **Cloud Run Service** ，自動解析 `Timeline.json` 、透過 Google Places API 查詢精確地標座標並匯出 `.esp` ；使用者下載 `.esp` 至本機 Earth Studio 算繪出 MP4 與 3D 追蹤 JSON 後回傳，再觸發 **Cloud Run Job** 執行 `route.py` 與 `compose.py` 合成配樂並輸出至 Cloud Storage。
2. **方案 B（全自動無頭 GPU 算繪架構）** ：
   以 **CesiumJS + Google Map Tiles API（Photorealistic 3D Tiles）** 取代手動操作的 Earth Studio。透過掛載 **NVIDIA L4 GPU 的 Cloud Run Job** 啟動無頭 Chrome，逐格控制 3D 相機並等待 `tilesLoaded` 事件完成後截圖；由於路線直接繪製於 3D 場景內，不僅能自然貼合地形並受山體遮擋，更能利用多個 Cloud Run Task 依 `CLOUD_RUN_TASK_INDEX` 平行切分影格合成，大幅縮短算繪時間。

## 🚀 結論與未來進階

透過將 **軌跡清理（KML 解析）** 、 **程式化運鏡（ `.esp` 逆向生成）** 、 **3D 實景算繪（Earth Studio）** 、 **WGS84 透視投影合成（Pillow + NumPy）** 與 **響度標準化配樂（FFmpeg）** 拆解為五個職責清晰的階段，我們成功把原本需要專業影視後製人員耗費數天手動對位的工作，濃縮為一套可重複執行、5 分鐘即可重新合成的自動化工程管線。

未來若想進一步擴充這支 3D 軌跡影片的豐富度，可以朝以下三個方向持續演進：
1. **景點停留時自動疊加旅途實拍相片卡** ：只需修改 `compose.py` ，在 `highlights` 的 `t0` 至 `t1` 停留期間，讀取對應時間戳記的 EXIF 照片並以拍立得卡片動畫淡入畫面一側，完全不需重新算繪 Earth Studio 底圖。
2. **升級 4K UHD 畫質輸出** ：由於 `.esp` 的關鍵影格全部採用 `0–1` 正規化數值，且 `compose.py` 的字級與線寬皆以 `s = H / 1080` 動態縮放，只需在 Earth Studio 算繪時將解析度改為 `3840×2160` ，即可無縫產出 4K 版本。
3. **社群平台輕量化轉碼** ：針對社群網路快速分享需求，可透過 `-b:v 12M -maxrate 15M -bufsize 24M -c:a copy` 將 `1.47 GB` 的母片壓縮至約 `250 MB` ，兼顧極速上傳與高畫質呈現。
